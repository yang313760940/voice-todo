票的依赖路线图

截至 2026-11-04：24 张票，全部 ready-for-agent、全部未认领、零代码。这张图回答一个问题：现在能开工的是哪张？

一句话结论 唯一没有阻塞、可以立刻开工的，是 #2。做完 #2，才解开 #3；#3 做完才解开 #4……整条链是一根清晰的顺序线，外加几处并行分叉。

怎么读这张图

每个方框是一张票。#2 … 这样的数字就是 GitHub 票号。箭头表示“先做左边，才能做右边”（即右边的票被左边阻塞，blocked_by）。绿色的是当前入口。

从 #4 之后并行推进的四条支线：
#5 清单闭环 #6 多提醒闭环 #14 离线输入完善 #17 番茄会话
提醒主线：
#6 多提醒 → #7 重复事项 → #8 重复变更 / #9 通知操作 → #10 提醒能力页 → #11 提醒恢复 → #12 解锁前提醒 / #18 备份恢复

另有 #13 事项朗读（被 #10 阻塞）。图里为可读性做了简化，精确 blocked_by 以 GitHub 票面为准。

为什么入口只有 #2

因为 #2 是“最小可跑闭环”——录音→离线转写→存一条事项→系统闹钟真的响。系统里其它所有票都直接或间接依赖它。在它跑通之前，做别的都等于在空中楼阁上加装修。

教学要点 “能不能开工”不是凭感觉，而是看两件事：① 有没有未关闭的阻塞票（blocked_by）；② 有没有人已经认领（assignee）。两者都空，才是“可接的票”（frontier）。这套工具链里这叫做“找 frontier”。

一张票“开工”的三步（写进肌肉记忆）

  1. 确认可开工：看 blocked_by 为 0、且没人认领。
  2. 认领：把票指派给自己（gh issue edit <号> --add-assignee @me），告诉所有人“这张我在做”。
  3. 开工：分支 → 写失败测试（红）→ 写代码让它过（绿）→ 复查 → 关票。
