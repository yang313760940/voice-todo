Lesson 02 · 拆小

一张 issue 就是一张“小任务卡”

把“做个 App”这种吓人的大目标，变成一张你一眼能审核的小卡片。

先说结论

上一课说「拆一小块」是循环的核心。那拆出来的那一块，具体长什么样？答案是一张卡片，叫 issue（读：伊-秀，意思是“议题/工单”）。在 GitHub 上，issue 就是一条带标题、带正文、可以打标签、可以指派人、最后能“关上”的记录。

一句话记住 issue = 一件足够小、小到能一次做完、能明确判断“做完没有”的事。它不是笔记，不是待办，而是“交给 AI/自己去做、做完能验收、验收过就关闭”的活。

好 issue 和坏 issue 长什么样

先看你 App 里的真实需求。你 docs/requirements-interview.md 里 Q14 定了首页是待办列表。下面两种写法，体会差别：

写法内容问题
❌ 太大 「做一个待办 App」 没法判断什么时候算做完；AI 会一口气写一堆你不认识的东西。
❌ 太虚 「优化一下首页体验」 “体验好”没有标准，无法验收，做法无穷多。
✅ 刚好 「首页顶部提供『收集箱 / 今天 / 最近七天 / 全部 / 已完成』五个入口，点击切换到对应列表」 有明确输入、明确行为、明确结果——一眼能判断做没做对。

判断标准只有一个：做完之后，你能不能指着一个东西说“这就是它”或“这不是它”。能，就是好 issue；不能，就还得再拆或者再想清楚。

一张好 issue 的四个零件

  1. 标题：一句动作。用动词开头，说清“做什么”。例：「首页加五个快捷入口」。别写成名词标题「首页」。
  2. 目的：为什么做。一句话说明它解决谁的问题。有了它，AI 才不会做偏。例：「让用户能按时间范围快速收窄要看的事项」。
  3. 验收标准：怎么算做完。列出可以逐条打勾的检查项。这是最重要的一栏——没有它，就没有“做完”。
  4. 边界：什么不做。明确划掉范围外的东西，防止 AI 顺手乱加。例：「本票不做排序，不做搜索」。
最值钱的一栏 是验收标准。初学者常省掉它，于是每次都要凭感觉争吵“这算不算做完了”。写成可勾选的一条条，你和 AI 就不吵架了——勾满即完成，勾不满就继续改。

issue 在本仓库里到底存在哪

你这个仓库的 AGENTS.md 已经定好了：issue 不在某个文件里，而是真的存在于 GitHub 上（用 gh 命令行操作）。所以“建一张票”= 在 GitHub 上真的开一条记录。这件事稍后我会带你实际做，今天先不急着动手。

小测验：你能挑出好票吗

1. 下面哪条最像一张合格的 issue 标题？

2. 一张 issue 里，哪一栏决定“这算不算做完了”？

3. 「边界：什么不做」这一栏，主要用来防什么？

这节课你拿到了什么

你现在能一眼判断：一张票是太大、太虚，还是刚好。你也能说出好票的四个零件，尤其知道验收标准才是灵魂。
