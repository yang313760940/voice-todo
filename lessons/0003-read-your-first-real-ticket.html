Lesson 03 · 读懂

读懂你仓库里第一张真票

今天不讲新命令。今天练一件更硬的本事：盯着一张真实的 issue，看出它好在哪、坑在哪。

先看事实：你的仓库已经有票了

上一课结束我打开了你的 GitHub 仓库，发现里面已经有两张票（不是我建的，是之前就存在）：

票号类型标题状态
#1规格 specAndroid 10+ 语音提醒应用首版：离线识别、可靠闹钟、待办、四象限与番茄ready-for-agent
#2实施票 ticket最小闭环：随包离线转写一条事项并触发系统闹钟ready-for-agent，无阻塞，可立即开工

而 #2 是 #1 的子票（它开头写着「Parent #1」）。也就是说：#1 是“整个 App 要成什么样”的大规格，#2 是“先做出最小可跑的一小块”的第一个实施票。#2 正好是第 2 课讲的“好 issue”的教科书样板。我们就用它当教材。

顺便记住这两个词 spec（规格）：一张大票，描述“整个东西要成什么样”，通常很大。ticket（实施票）：挂在 spec 底下、一次能做完的小块。看 #2 开头那行 Parent #1，就是“我是 #1 的孩子”。

逐段拆开 #2，看四个零件在不在

下面左边是 #2 原文，右边是我给你标的“这是哪个零件”。试着先自己读一遍原文，再看右栏。

原文（#2 摘录）这是哪个零件 / 好不好
标题：最小闭环：随包离线转写一条事项并触发系统闹钟 标题 ✓ 用“最小闭环”点明范围，一句话说清做三件事（录音转写→存事项→闹钟）。不是名词堆。
## 目的：
尽早把两项核心技术风险串成可运行路径，而非先做空工程或纯模型层。		 目的 ✓ 说清了“为什么先做这块”——先验证最危险的两个技术点，而不是先搭空架子。这是成熟做法。
## 验收标准：
6 条，每条以 - [ ] 开头，能逐条打勾。		 验收标准 ✓✓ 这是灵魂。等下我们逐条看。
## 边界：
只做一条非重复事项、一次指定时刻闹钟；不做 AI、复杂时间…		 边界 ✓ 明确划掉了范围外的东西，防 AI 顺手乱加。

四个零件齐全。这是一张质量很高的票——你以后自己拆票，就照它这个长相拆。

验收标准为什么值钱：逐条看

#2 的六条验收标准，每一条都在防一个具体的“假成功”：

  1. 能构建、minSdk=29、模型许可已记录 —— 防“根本没打包进去模型就说做完了”。
  2. 断网冷启动、用真实随包模型识别固定普通话音频，非假转写、非首次下载 —— 这句最关键。“非假转写”四个字直接堵死了“AI 假装识别成功”这种糊弄。
  3. 手选时间→持久化；取消确认不创建；重开可见 —— 防“点保存其实没存”。
  4. 系统 PendingIntent 闹钟真实触发…不是应用内计时器模拟 —— 又一个“非假成功”。应用自己计时假装响铃是常见偷懒。
  5. 权限最小检查；未具备权限时不误报已安排 —— 防“其实没权限，界面上却显示已安排”。
  6. 可重复的演示步骤 + 集成测试结果 —— 要证据，不要口头保证。
这正是你“读懂”的核心能力 好的验收标准每一条都在描述一个“假成功”并堵住它。看到“非假转写”“不是应用内计时器模拟”这种措辞，你该立刻明白：作者预判了 AI 最可能糊弄的地方。你以后要做的，就是像这样把“糊弄点”提前写进验收标准。

现在轮到你了：发现一个该由你拍板的分歧

把 #2 的边界读完，你会发现一句关键的话：

「真机验收在独立后继票，本票交付可测 APK 及模拟器证据，不声称真机已验证。」

意思：#2 这张票只要求“在模拟器上能跑”，真机验收要另开一张票。而上一轮你告诉我：你有一台真实的安卓手机。这里就出现了真实的岔路——是一个完美的“说不 / 说改”练习点。两条路各有道理，你来选：

选项好处代价
A. 保持原样：先模拟器跑通，真机另开票 块更小、更快拿到第一个“跑起来”的胜利。 模拟器能过、真机照样翻车（尤其闹钟/权限），得多走一轮。
B. 改这张票：把“真机也能响”加进 #2 验收 第一个闭环就在你自己的手机上响，一次验证到底。 这张票变大、变慢，第一次“跑通”要更久。

这里的教学点不在“哪个对”，而在：一张票的边界不是天书，你能看懂、能质疑、能改。“说改”是这套工具链里最值钱的人类动作之一。

小测验：你读懂了没有

1. #2 开头那行「Parent #1」是什么意思？

2. 验收标准里「非假转写」「不是应用内计时器模拟」这类措辞，作用是什么？

3. 你读到 #2「真机验收在独立后继票」，而你正好有安卓真机。这时你该做什么？

这节课你拿到了什么

你能拿着一张真实的 issue，逐段说出四个零件在不在、好在哪；而且你知道验收标准 = 提前堵住“假成功”。更重要的是：你发现了一张票里的真实分歧，并知道“说改”是你该做的动作——我已经准备好了，只要你下决定，我就能真的去改 GitHub 上那张 #2。

想再深入，读这个（一手资源）

👉 GitHub 官方 ——《Creating an issue》。看标题、正文、任务清单（- [ ]）分别怎么用——你刚在 #2 里看到的，就是这些字段的组合。
