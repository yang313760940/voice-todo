Lesson 05 · 读懂票的类型

别把“规格”当成“活”

#1 也显示“可以实施”了——但这不代表你该去“执行它”。这一课讲清 spec 和 ticket 的根本区别。

先回答你的问题

#1 不需要你去“执行”。你看到“#1 也可以实施”，是因为工具对“无阻塞的票”统一这么提示，它不区分票的类型。而 #1 是一张 spec（规格），不是一张能动手做的活。

一句话记住 spec 的“实施” = 它下面的 ticket 被一张张做完。spec 自己永远是“容器”，不是一个你要亲手完成的任务。你去“做”一张规格，就像去“做”一份菜单——菜单本身不能吃，吃的是上面一道道的菜。

spec 与 ticket 的根本区别

#1 spec（规格）#2 ticket（实施票）
回答的问题整个 App 最终要成什么样这一小块具体做什么、怎么验收
大小很大，覆盖全部 70 条用户故事很小，一次能做完
能被“做完/关闭”吗只有当它下面所有票都做完，才可能关闭做完当前这一块就能关闭
你要对它做什么阅读、理解、必要时修订——不“执行”认领、动手、验收、关票——这才是活
它和其它的关系是父，下挂 #2–#24 共 23 张子票是子，挂在 #1 底下

其实你已经在 GitHub 上见过证据：打开 #1，它的子票列表里挂着 #2 到 #24，整整 23 张。这就是“容器”的样子。

那“实施 #1”到底是什么意思

当你看到 #1 标着“可以实施 / ready”，正确的理解是：

  1. 它不阻塞任何东西——它作为规格已经写清楚了，不需要再等谁。
  2. 它下面的票可以按依赖逐步开工——从 frontier 上唯一那张 #2 开始。
  3. “实施整个 #1” = 把 #2→#24 全部做完、验收、关闭，那是整个项目的大终点，不是今天的一个动作。
初学者最容易踩的坑 把规格当成一个大任务，直接“执行规格”，结果 AI 一口气想覆盖 70 条故事，写出一大坨没人能验收的东西，最后推倒重来。规格是用来“读”和“拆”的，不是用来“一次性干完”的。

所以你现在该做的，还是同一件事

答案没变，还是第 4 课那句：只做 frontier 上那一张，#2。#1 的“可以实施”不改变这一点——它只是告诉你“规格本身没问题，放心去做下面的票”。

说一句实话：我查了 GitHub，#2 目前还没有被认领（assignee 为空），也还是 OPEN。你说“#2 已经开始执行”，可能是你在别的窗口动了手。不管怎样，票面上先“认领 #2”这一步不能省——它是让所有人（和所有 AI）知道“这张已被占用”，避免重复施工。

顺便：一张票什么时候才算“关掉”

既然讲到“做完”，就顺带说清楚。关一张 ticket 的条件：它的验收标准全部打勾。比如 #2 的六条——能构建、离线真转写、能存能读、真闹钟响、权限检查、有可重复的演示证据——全绿，才关 #2。关掉 #2 的那一刻，#3（真机验收）才从“被阻塞”变成“可开工”。这就是循环“关上这张、回到第一步走下一圈”的真实样子。

2. spec（规格）和 ticket（实施票）最大的区别是什么？

3. 什么时候才算“实施完了 #1”？

这节课你拿到了什么

你能一眼分辨 spec 和 ticket，不会再被“可以实施”的提示带偏去“做规格”。你也知道了 ticket 关闭的唯一标准是验收标准全绿，以及关一张票如何让下一张票解锁——这正是五步循环“走下一圈”的齿轮。
